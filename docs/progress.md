- Decided 2026-11-24, chief's decision C224 (not the user's words; the user may reverse it): option (a), a known limitation with one README line (the 1.70 row above). The question as asked: **Q1 (1.69): after a boot with the clock far behind, lines logged before the clock was corrected are not read: a known limitation?** What the operator sees: at a restart firewatcher reads the journal from `--capture-time` (300 s by default) before the saved line; lines logged while it was stopped and stamped earlier than that are not read. That needs a boot whose hardware clock was more than `--capture-time` behind and was corrected before firewatcher started, and a journal that lost the saved line (as a volatile journal does at a reboot). 1.68 does the same, and was worse (it skipped the whole second it could not find). Why not fix: where the saved line is gone, firewatcher can only go by time, and so does journalctl (a cursor from another boot lands by its time; tested on systemd 219 in the 1.70 design check of 2026-11-23); the cursor design planned for 1.70 does not change this case. Where the saved entry is still there (a persistent journal), the cursor resumes exactly whatever the clock did. Revisit when an operator hits it. It would also get one README line. Options: **(a) known limitation (recommended)**; (b) a fallback that reads by boot instead of by time, in a later version (planned work, so a deferral instead). What waits on it: nothing (the entry is written once you answer). Your words it touches: none. (Corrected 2026-11-23 after the design check: the earlier text offered resuming by cursor as the fix.)
