# Lessons: full entries

Why this project's APIs, formats and agreed behaviours had to change. `lessons.md` has one line per
entry: read that first, and look entries up here by date and name rather than reading this whole. New
entries go last, in the same commit as the change:

```markdown
## YYYY-MM-DD <short name>
- Changed: ...
- Why we had to change: ...
- Original design was wrong because: ...
- Lesson: ...
```

## 2026-10-27 firewatcher: the model's excerpt is built from where the events are, not from the file's ends
- Changed: the excerpt of a large capture sent to the LLM is the header, the lines before the match, the lines after it and the end of the capture, located by byte offsets capture_messages records as it writes (GitHub 1.61/1.62 of 2026-10-23, first published to PyPI as 1.63). 1.60 sent the first 2 KB and the last ~46 KB.
- Why we had to change: captures hold 5 minutes before and after the match, so in 35 of 49 captures on one server in October the matched event was in the gap and the model judged an incident it never saw. Keeping the end matters too: on 2026-10-23 a failed backup's retry succeeded in the last minutes of the capture, and that is what kept the model from pushing.
- Original design was wrong because: it cut by position (start and end) a record whose important part sits at a known place in the middle, and it located nothing by what the writer already knew (where it wrote the match).
- Lesson: when a record must be cut to a budget, record where its important parts are while writing it, cut around those, and keep the end where outcomes show. A budget split must never shrink a piece when the budget grows (a superseded attempt that did kept producing new edge cases).

## 2026-10-27 firewatcher: --requires-mounts-for paths are normalized as text, never resolved on disk
- Changed: in 1.64 each `--requires-mounts-for` path is made absolute and normalized as text (`.`, `..`, `//`, a trailing `/`), from its bytes, and quoted with `%` doubled. A path with a newline or carriage return, or one that is not UTF-8, is refused before anything is installed. Before, the path was written raw. Symlinks are not followed and the file system is not touched.
- Why we had to change: systemd splits an unquoted path at spaces, expands `%`, and ignores relative and unnormalized paths. So a unit could wait on the wrong mount, or on none, and start before an NFS share was up, with only a warning in the journal.
- Original design was wrong because: it passed operator text into a file with its own syntax (unit-file quoting, specifiers, path rules) as if it were plain text, and nothing checked what systemd read back. Two later attempts were wrong as well. Refusing `..` broke input that was accepted before. Resolving with realpath could follow a symlink off the remote share, hang on a dead hard-NFS mount, trigger automounts, and make the result depend on what was mounted at install time.
- Lesson: when you write a value into another program's file format, test what that program reads back for each odd input, against the real program. Transform the value only as the reading program would (here as text, like systemd), never by consulting state that may be absent or hung at the time you write.

## 2026-11-03 firewatcher 1.65: the verdict moved to the receiver
- Changed: with `[notify] events_url` set, every finished capture is POSTed as JSON (with an excerpt of up to 16 KiB) and firewatcher's own LLM analysis is off, whatever `[llm] enabled` says; a startup line says so. The event's `push` is the rule-based floor, `always_notify`. `model_notify` stays in the event, always `null`. A 2xx answer means the receiver has the capture and nothing goes to ntfy. When the POST fails, only `always_notify` captures are pushed to ntfy; the others stay in the capture folder and the journal.
- Why we had to change: the first events_url design (before 1.65 was released) kept firewatcher's own LLM judging the push, and housekeepd followed it, so behaviour stayed the same while events_url was new. Once housekeepd had its own triage, with the host's tools and history, there were two judges, two verdicts, double LLM traffic, and an outside LLM service saw every capture.
- Original design was wrong because: it kept the judgment at the sender after a better-informed stage existed downstream.
- Lesson: when a pipeline gains a smarter stage downstream, move the judgment there whole, and keep only the rule-based floor (`always_notify`) at the source.

## 2026-11-03 firewatcher 1.65: a URL is parsed once, by our own strict rule
- Changed: one strict check (`_is_http_url`) decides whether an LLM, ntfy or events URL is usable. The request and every log line use only what that check matched; a `user:password` is stripped and never sent or logged, and a URL is shown only as its server (`scheme://host[:port]`). Before 1.65 the check only needed an `http://` or `https://` start with no whitespace or control characters. Now firewatcher also stops at startup for: a server part that is not a host name (no `/`, `?`, `#`, `@`, `[`, `]`, `:` or `%`) or a bracketed IPv6 address, followed by an optional port of up to 5 digits (0 to 65535), judged also after Unicode NFKC normalization; a `user:password` that holds a `/`, `?` or `#`; and a URL with a `user:password` and another `@` later in its path, query or fragment. A URL without `user:password` may still hold an `@` in its path. With events_url set, a bad `[llm]` URL no longer stops firewatcher, since the LLM does not run.
- Why we had to change: a password holding an `@` before a `/`, `?` or `#` left the text between them as the host, and the host is logged. Review took five fix rounds on this check (credentials in requests and logs, unparseable URLs echoed, a password holding an `@`), and the last one replaced the library's view of the authority with our own check that gives the same answer on every Python.
- Original design was wrong because: it used a lenient library parser for a value that is both sent in requests and written to logs, and the old check accepted nearly anything with an http prefix.
- Lesson: when a value is both used for requests and written to logs, parse it once with our own strict rule that behaves the same on every runtime, not a lenient library parser. Record what that refuses that used to be accepted, as the entry above does.

## 2026-11-14 firewatcher 1.68: --install-service checks and renders everything before it writes
- Changed: `--install-service` refuses a unit name systemd cannot load or enable (characters other than letters, digits and `: _ . @ - \`, more than 255 with the `.service` suffix, an `@` without a name before it or an instance after it) and a path or value that is not UTF-8 (on Python 3.6 under a C locale that is every non-ASCII one: it is refused, not restored, because the service under the same locale could not encode it either), with exit 2, before it creates the output folder, seeds patterns or writes the config or the unit. It renders the unit and the new config first and writes the text it rendered. A blank `--unit-name` means the default. 1.67 took any name as a file name and wrote the config before it had rendered the unit.
- Why we had to change: a name such as `a/b` stopped the install with a traceback after the config was written, and that left-over config made the next install render a different unit (flags on `ExecStart` instead of in the config). A name such as `fwé` was written as a file systemd skips, so `enable` failed, and with `--no-enable` the install reported success. A non-UTF-8 value stopped it with `UnicodeEncodeError`, again after the output folder and patterns were made.
- Original design was wrong because: it treated an install as a series of independent writes, so a step that failed late left the earlier ones behind as state the next run read (1.68 closes that for the checks and the rendering; a failed `daemon-reload` or `enable --now` after the writes still leaves the config and the unit, which a rerun reads: deferred to 1.69); and it checked the unit name only as a file name, not by the rules of systemd, which is what loads it.
- Lesson: an install that writes several files checks and renders all of them, by the rules of the program that will read each one, before it writes any, so a refusal leaves nothing behind. A step that fails after the writes (a systemctl call) still leaves them: a half-done install is state that changes what the next install does.

## 2026-11-23 firewatcher 1.69: the service reads UTF-8 paths in any locale, so the install no longer refuses a non-ASCII one
- Changed: on Python 3.6 under a C locale, `--install-service` writes a non-ASCII path or note given on the command line (which Python hands over as escaped bytes) into the config or unit as the UTF-8 text its bytes spell; 1.68 refused it with exit 2. Bytes that are not UTF-8 are still refused. The service in turn takes each path from the config as the string Python's file calls take for its UTF-8 bytes, logs and sends escaped bytes as UTF-8 text, writes paths into captures and `journal.log` as their own bytes, prints what stdout cannot encode with backslash escapes, and reads pattern files as UTF-8 in every locale.
- Why we had to change: 1.68's refusal stopped one writer, an install from a C locale, but the service still died with `UnicodeEncodeError` on a config written under a UTF-8 locale and started under a C one, on a hand-written config, on a path given by hand, and on any matched log line that was not ASCII.
- Original design was wrong because: it refused the value where it was written because one reader, the service under that locale, could not use it, instead of fixing that reader. The refusal covered one path into the reader and left the others.
- Lesson: when a value is refused only because a later reader cannot handle it, fix the reader and drop the refusal: the refusal closes one way in and leaves every other way the value reaches that reader failing. A value that is not UTF-8 is still refused.

## 2026-11-23 firewatcher 1.69: the replay finds the saved line in the journal as it is now
- Changed: before resuming, firewatcher reads the saved second of the journal once. The replay ends at the saved line by its number in that second when the journal still has it there, else, while the journal holds a line with its digest after that number, at that line, as in 1.68; else at the first line of that second with its digest; with no such line nothing is replayed and every line from `--capture-time` before it (no further back than `--resume-max`) is matched. 1.68 needed the number and the digest together, counted from the first line of that second it was shown, so a lost start of the second never reached the number.
- Why we had to change: when the journal lost the start of the saved second while firewatcher was stopped (a journal file rotated away), the number was never reached and the rest of that second was context only, never matched. When it lost the line itself and the clock came back behind it by up to a minute (a reboot with a volatile journal and a wrong hardware clock; beyond a minute the position is ignored and the last lines are read), every line stamped before the saved second was context, until the clock passed it.
- Original design was wrong because: it took a position counted from the start of a group (the lines of one second) as stable, in a log another program rotates while firewatcher is stopped, and its only way out of the replay was a later timestamp.
- Lesson: a position counted within a log that another program trims is checked against the log as it is now before it is trusted; when it cannot be found, read again rather than skip.

## 2026-11-23 firewatcher 1.69: the saved second ends at a distance from it, not at the first line of another second
- Changed: reading the saved second of the journal (`locate`), firewatcher collects the lines shown as that second and stops at the first line shown more than `JOURNAL_STAMP_SKEW` (30) seconds after it, or, once it has read a line of that second, more than that before it. A line shown far before the second's first line is passed over, because a stall of journald stores the lines that waited for it first: an earlier version of this rule stopped at any far line, so such a head ended the read before the saved second, the note said the journal no longer held the saved line, and the whole window was matched again where 1.68 resumed exactly. 1.69 as built stopped at the first line of any other second. The replay itself (`replay_time`) still ends at the first line shown later than the saved second, as in 1.68: a line stored before the saved one and shown a second later ends it early, and lines read before the stop match again (a second capture, never a skip). Its stop rule is the 1.70 plan of the deferral in `limitations.md`, designed with the numbering that entry plans.
- Why we had to change: journalctl shows a line with the time it was sent but seeks and orders by the time journald stored it, a little later. So `--since=@S` can start with a line shown as the second before, and a line shown as S can follow one shown as S+1. Reading stopped at the first of them, the saved line was not found, and an ordinary restart matched the whole `--capture-time` again (a second capture and push of the last incident). On the journal of the host it was built on, 90 of 187,902 seconds that held lines were read that way, and 1,303 of 1,819 lines in them would have matched the whole window again. In 34.7 days of that journal 4.5 million entries carry a sent time: 99.995% were stored within a second of it, the largest gap outside two stalls of the host (370 and 458 s) was 15.7 s, and 30 covers that about twice.
- Original design was wrong because: it read the time a line shows as the order the lines come in, which is the stored time. The tests' fake journalctl sought by the time a line shows, so it could not tell the two apart.
- Lesson: a reader that stops on a timestamp it reads from the lines must know which time the program that orders the lines uses; stop on a distance from it, never before the first line you want (a stall stores far earlier lines first), and test against a source that keeps the two apart. Apply it to every reader of the same lines: the replay still stops at the first later line (1.70).

## 2026-11-23 firewatcher 1.69: a failed install undoes what it did, in the order the tools need
- Changed: when a step of `--install-service` fails after the writes, it disables the unit if this run enabled it (it asks `systemctl is-enabled` before `enable --now`), then removes the config and the unit it created, puts back the old text of a unit it replaced, and reloads systemd. A `systemctl` that cannot be run, a file that cannot be removed and a config that does not fit on the disk are the same kind of failure, with a message. The config is written to its end or removed: 1.68 and 1.69 as built took a short write as done.
- Why we had to change: removing only what was created left a replaced unit pointing at the config that was removed (a restart loop on `config file not found`); `disable` came after the unit file was removed, which systemd 219 refuses (the wants link stayed); a unit this run replaced and its failed `enable --now` had enabled stayed enabled (the disable ran only for a unit the run created), and a disable after every failure would have disabled a unit that was enabled before the install; and systemd kept the removed unit's new text loaded until the next reload.
- Original design was wrong because: it undid the files, not the steps, and took a unit the install overwrote for something it had not touched.
- Lesson: an install that can fail part-way records what each step changes before it runs it (the old text, whether the unit was enabled), and undoes only that, in the order the program that reads the files needs.
